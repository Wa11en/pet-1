# Сервер оплаты Private Diary Pro

Этот отдельный сервер принимает оплату **99,00 ₽ за календарный месяц** через СБП в YooKassa и выдаёт приложению подписанный сертификат Pro. Продление ручное: каждый платёж подтверждает покупатель. Способ оплаты не сохраняется, регулярных списаний и API автоплатежей нет. Дневник, поиск, шифрование, импорт и резервные копии не зависят от этого сервера; Pro отключает рекламу и открывает локальную статистику.

В репозитории нет действующего магазина, сервера, платёжных ключей или приватного ключа подписи. При отсутствии настроек API отвечает `503`, покупка недоступна. Никаких тестовых активаций Pro в публичных маршрутах нет. Тестовый провайдер существует только в unit-тестах и передаётся через конструктор.

## Перед приёмом настоящих платежей

1. Подключить собственный магазин YooKassa как самозанятый, согласовать СБП и проверить доступность метода в договоре. Сведения провайдера: [платежи для самозанятых](https://yookassa.ru/platezhi-dlya-samozanyatyh/), [интеграция СБП](https://yookassa.ru/developers/payment-acceptance/integration-scenarios/manual-integration/other/sbp).
2. Согласовать с YooKassa выдачу покупателю чека именно для подключённой схемы НПД. Этот адаптер **не формирует фискальные чеки и не принимает email/телефон покупателя**. Код не доказывает, что конкретный договор автоматически выдаёт нужный чек. Если провайдер не обеспечивает согласованную схему без передачи этих данных, адаптер нужно доработать до запуска. Только после подтверждения оператор устанавливает `PROVIDER_MANAGED_RECEIPTS_CONFIRMED=true`. По умолчанию этот флаг выключен и блокирует оплату.
3. Разместить сервер на собственном HTTPS-домене, опубликовать реальные оферту, политику обработки платёжных данных, условия возврата и контакты продавца. Почта поддержки проекта: `gr1val@yandex.ru`. Договор эквайринга, реквизиты продавца и обязательные сроки хранения платёжных данных определяет владелец сервиса.
4. В кабинете YooKassa указать `https://<ваш-домен>/v1/webhooks/yookassa` для `payment.succeeded`, `payment.canceled` и `refund.succeeded`. Код также безопасно обрабатывает `payment.waiting_for_capture`, но использует одностадийную оплату `capture=true`.
5. Пройти сценарии в тестовом магазине YooKassa, затем сверить небольшой настоящий платёж, чек, возврат и повторное уведомление. Unit-тесты ниже не заменяют эту проверку договора и боевого магазина.

## Запуск

Требуется Python 3.12+. Зависимости зафиксированы в `requirements.txt`; Python-сервер не включается в Android APK.

```bash
cd backend
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

В отдельном защищённом каталоге сервера создайте выделенный RSA-ключ минимум 3072 бита. Приватный ключ не должен попадать в Git, приложение, CI-артефакты или общую рабочую папку:

```bash
umask 077
mkdir -p /var/lib/private-diary /run/secrets
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 -out /run/secrets/private-diary-license.pem
openssl pkey -in /run/secrets/private-diary-license.pem -pubout -out /var/lib/private-diary/license-public.pem
chmod 600 /run/secrets/private-diary-license.pem
```

Запускайте эти команды с правами, подходящими для вашего сервера; файл должен читать только пользователь процесса. `/run` может очищаться после перезапуска: в production используйте постоянное хранилище секретов и безопасное монтирование при запуске. Из публичного ключа для конфигурации Android нужен **SPKI DER, закодированный обычным Base64**, без PEM-заголовков:

```bash
openssl pkey -pubin -in /var/lib/private-diary/license-public.pem -outform DER | openssl base64 -A
```

Нужны переменные из [.env.example](.env.example). Файл `.env` сам автоматически не читается: передайте переменные через systemd `EnvironmentFile`, контейнерные секреты или окружение процесса. Пример сервиса находится в [deploy/private-diary-payments.service](deploy/private-diary-payments.service); замените пути и создайте отдельного непривилегированного пользователя.

```bash
umask 077
.venv/bin/uvicorn diary_payments.app:app --host 127.0.0.1 --port 8080 --workers 1 --proxy-headers --forwarded-allow-ips 127.0.0.1 --no-access-log
```

Uvicorn должен слушать только loopback; снаружи работает HTTPS reverse proxy. Доверяйте заголовкам proxy только с адреса вашего proxy. Он должен **заменять** клиентские `X-Forwarded-Proto`/`X-Forwarded-For`, ограничивать размер запроса 16 КиБ и соединения, отключать запись query string, `Authorization`, request/response body и URL оплаты в access/APM-логи. Не подключайте аналитику, error-reporting SDK или логирование HTTP-тел. Встроенный лимит: 60 запросов в минуту на источник, из них не более 5 попыток checkout; память ограничена 4096 источниками. Для нескольких процессов/серверов нужен общий лимит на proxy.

`GET /health` возвращает `paymentsConfigured`; не публикуйте его как диагностический endpoint для посетителей. Остальные маршруты отклоняют HTTP (`426`). Значение `PAYMENTS_PUBLIC_ORIGIN` — проверяемая настройка публичного HTTPS origin, а маршрутизацию/сертификат обеспечивает оператор proxy. На `PAYMENTS_RETURN_URL` разместите свою статичную HTTPS-страницу, например [deploy/return.html](deploy/return.html). Она только предлагает вернуться в приложение; успешное открытие страницы никогда не активирует Pro.

Храните SQLite и её WAL/SHM в закрытом каталоге (`0700`), файлы — `0600`, с `UMask=0077`. Делайте согласованные резервные копии SQLite с ограниченным доступом. Автоматического удаления платёжных записей пока нет: перед релизом оператор должен определить и реализовать сроки хранения по своему договору и применимым требованиям. Удаление всех записей без сохранения реестра использованных платежей небезопасно: оно ломает восстановление и защиту от повторного начисления.

## Контракт приложения

`accountToken` — созданный приложением случайный секрет 32 байта, Base64URL без `=` (ровно 43 символа). Это код восстановления покупки. Сервер хранит только SHA-256, исходный секрет не записывает. Пользователь должен сохранить код отдельно: email-аккаунта и восстановления по почте нет. Кто знает код, тот может восстановить доступ на другом устройстве. Передача идёт только по HTTPS, ответы имеют `Cache-Control: no-store`.

### Создать платёж

`POST /v1/checkout`

```json
{
  "installationId": "b73cb8f1-b9af-42bb-826f-ab67972842ec",
  "accountToken": "<32 случайных байта в Base64URL>",
  "requestId": "<новый UUID для одной покупки>",
  "planId": "pro_monthly"
}
```

Ответ:

```json
{
  "checkoutId": "<UUID>",
  "paymentUrl": "https://yoomoney.ru/checkout/...",
  "amount": "99.00",
  "currency": "RUB",
  "period": "month"
}
```

Цену, валюту, `capture=true`, СБП и `save_payment_method=false` задаёт сервер. Поля `price`, `amount`, email и текст дневника отвергаются, как и любые лишние поля. Разрешены только HTTPS URL оплаты на точных доменах или поддоменах `yoomoney.ru`, `yookassa.ru`, `pay.nspk.ru`, с проверкой границы DNS-имени; credentials и нестандартные порты запрещены.

Приложение сохраняет `requestId` **до** запроса. При таймауте повторяет именно его: используется тот же ключ идемпотентности YooKassa. Пока есть незавершённый checkout, новая попытка с другим `requestId` вернёт `409`; завершите/проверьте старую попытку. При неопределённом результате без сохранённого `payment_id` спустя 23 часа автоматический повтор блокируется: срок действия ключа идемпотентности провайдера ограничен, нужна сверка с поддержкой, чтобы исключить повторное списание. После такой сверки оператор исправляет состояние средствами администрирования БД с аудитом; публичного endpoint «активировать Pro» нет.

Защита от избыточной предоплаты: не более одного незавершённого checkout и не более 12 календарных месяцев вперёд. Сервер не предлагает автоматическое списание по истечении срока.

### Проверить платёж

`GET /v1/payments/<checkoutId>?installationId=<UUID>`

Заголовок: `Authorization: Bearer <accountToken>`.

```json
{"status":"pending","entitlement":null}
```

Статусы: `pending`, `paid`, `canceled`. Только проверенный `paid` даёт строку `entitlement` вместо `null`. URL возврата, ответ приложения и входящее webhook-уведомление сами по себе оплату не доказывают. Сервер запрашивает известный `payment_id` напрямую у YooKassa и сверяет `paid`, статус, сумму, валюту, получателя-магазин, СБП и `metadata.checkout_id`. Неподтверждённый, чужой, отменённый или несовпадающий платёж не даёт доступ.

### Восстановить покупку

`POST /v1/restore`

```json
{"installationId":"<UUID текущего устройства>","accountToken":"<сохранённый код>"}
```

Ответ: `{"entitlement":"<подписанная строка>"}` либо `{"entitlement":null}`. До выдачи сертификата сервер повторно сверяет ещё действующие начисления и незавершённый платёж у провайдера, максимум 13 записей, параллельно не более четырёх. Таймаут socket на одну проверку — 3 секунды; история прошлых лет не создаёт сотни запросов. Ошибка любой нужной проверки возвращает `503`. Возвраты уже истёкших платежей обрабатывает webhook; оператору нужна периодическая сверка реестра с YooKassa на случай пропущенных уведомлений, автоматического задания для неё пока нет. Новый сертификат привязывается к текущему `installationId`, а история оплаты остаётся у кода восстановления.

Ошибка `401` означает неверный код/чужой платёж; `409` — незавершённый checkout или лимит предоплаты; `422` — неверные/лишние поля; `429` — частые обращения; `503` — неподключённый сервер или неподтверждённый ответ провайдера. Ответы об ошибках не возвращают исходные секреты или детали API YooKassa.

## Сертификат и начисление

Формат: `v1.<Base64URL(JSON UTF-8)>.<Base64URL(signature)>`, без `=`. Подпись — RSA PKCS#1 v1.5 с SHA-256 над ASCII-строкой `v1.` и закодированным payload. Единственный доверенный публичный ключ зашит в конфигурацию Android; алгоритм и URL ключа не берутся из токена.

Payload содержит ровно шесть полей:

```json
{"version":1,"aud":"ru.privatediary","sub":"<installationId>","plan":"pro_monthly","issuedAt":1795348800000,"expiresAt":1797940800000}
```

Времена — целые миллисекунды Unix. Месяц считается по UTC, с сокращением дня до последнего дня следующего месяца: 31 января → 28/29 февраля. Подтверждение повторного webhook, параллельная проверка и повторный запрос не добавляют ещё месяц: начисление выполняется атомарно в SQLite один раз на платёж. Ручное продление добавляет месяц к большему из текущего срока и времени подтверждения.

Подтверждённый провайдером частичный или полный возврат отзывает серверное начисление соответствующего платежа; остальные начисления пересчитываются по времени их подтверждения. Уже выданный **офлайн** сертификат в этой версии остаётся действительным до своего срока: мгновенный отзыв, включая принудительный сброс локального сертификата при онлайн-проверке, не реализован. После возврата сервер не выдаёт новый доступ за отменённый платёж. Это ограничение нужно учесть в опубликованных условиях возврата. Смена приватного ключа требует обновления доверенного публичного ключа в приложении; механизма ротации нескольких ключей пока нет.

## Данные и тестирование

Сервер хранит псевдонимные UUID установки/покупки/запроса, идентификатор и защищённый URL платежа, статус, даты, срок Pro, признак возврата и хеш кода восстановления. Сервер не получает записи дневника, теги, настроение, статистику, поисковые запросы, файлы и резервные копии. Внутренний лимитер держит только случайно посоленные хеши адресов источника в оперативной памяти в минутном окне; сетевой адрес неизбежно доступен инфраструктуре HTTPS/провайдеру, это не следует скрывать в политике.

```bash
cd backend
.venv/bin/python -m pip install -r requirements-test.txt
.venv/bin/python -m unittest discover -s tests -v
```

Тесты используют временную SQLite и внедрённый in-memory провайдер, не обращаются к YooKassa и не списывают деньги. Покрыты неподтверждённый/поддельный webhook, чужой магазин, сумма/валюта/СБП, отмена и возврат, повтор/параллельное подтверждение, месяцы и високосный год, права на ключ, восстановление на новой установке, идемпотентность, конфиденциальность кода, HTTPS, ограничения размера/частоты и fail-closed конфигурация.

Публичная [tests/fixtures/license.json](tests/fixtures/license.json) создана отдельным одноразовым тестовым RSA-ключом в памяти, приватный ключ не сохранён. Эту подпись проверяют Python-тест и JVM-тест приложения. Она предназначена только для проверки совместимости, не для production-конфигурации.

Ограничения текущей поставки: один процесс/SQLite, нет панели поддержки и автоматической очистки, нет ротации подписывающих ключей, восстановления без кода или автоматического возврата денег. Размещение сервера, подключение магазина, чековая схема и настоящий платёж ещё требуют действий владельца. Адаптер провайдера имеет интерфейс `create/get`, поэтому PSP можно заменить отдельно от дневника и UI.
