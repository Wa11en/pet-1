# Бесплатный релиз в RuStore и Pro через СБП

Установка бесплатна. Создание и редактирование записей, поиск по словам и смыслу, шифрование, блокировка, импорт, Markdown и зашифрованные резервные копии остаются бесплатными и работают без сети. Отказ от рекламы, отсутствие сети или окончание Pro не закрывают дневник и не удаляют записи.

**Pro — 99 ₽ за календарный месяц**: отключение рекламы и локальная статистика настроения, тегов и регулярности записей. Каждое продление пользователь отдельно оплачивает через СБП в платёжной форме YooKassa. Автосписаний, сохранения платёжного средства для регулярных списаний и автоматического продления нет. Это помесячный доступ с ручным продлением, а не рекуррентный банковский платёж. Цена установки — 0 ₽.

**Статус: техническая подготовка, не готовая коммерческая публикация.** Рекламный блок, production-сервер оплаты, ключ проверки лицензии, аккаунт YooKassa, СБП и порядок выдачи чеков ещё не настроены. Пустые настройки не заменяются демонстрационными платежами или лицензией: оплата и показ рекламы недоступны до конфигурации. Отправка в магазин, заключение договоров и настоящий приём денег выполняются владельцем после проверки.

## Данные и варианты сборки

Сведения для выпуска: [release-config.json](release-config.json). Карточки: [RU](store/metadata-ru.json), [EN](store/metadata-en.json). Почта поддержки: `gr1val@yandex.ru`. Юридическое имя владельца и реквизиты не предоставлены; их нельзя подменять вымышленным ИП или компанией.

| Вариант | Назначение | INTERNET | Монетизация |
| --- | --- | --- | --- |
| `offline` | Отдельная полностью офлайн-сборка | Запрещён проверкой объединённого манифеста | Без рекламного SDK и сетевой оплаты |
| `store` | Бесплатное приложение для RuStore | Есть для явных действий с рекламой и оплатой | Реклама Яндекса и Pro через собственный сервер + YooKassa СБП |

Оба варианта содержат одну локальную модель и зашифрованный дневник. Разрешение INTERNET действует на весь пакет Android: его нельзя технически включить только на время рекламы. Для `store` контролируется поведение кода: реклама открывается пользователем в отдельном процессе с пояснением о сетевых данных; сетевые действия оплаты и восстановления Pro запускаются кнопками. Автозагрузки модели, облачной обработки записей и сетевой проверки при каждом открытии дневника нет.

## Что владелец подключает перед выпуском

1. **Аккаунт разработчика RuStore.** Создать бесплатное приложение, подтвердить данные владельца, доступность `ru.privatediary`, возрастную категорию и договор. Возможность бесплатной публикации и условия сторонней оплаты уточнить в актуальной консоли. Платёж не проводится через RuStore Pay SDK; в анкете нужно явно раскрыть рекламу и прямую оплату цифрового доступа через СБП. Не считать такую схему автоматически согласованной магазином.
2. **YooKassa и НПД.** У владельца статус самозанятого физлица. Уточнить у YooKassa возможность договора именно для этого статуса, доступность СБП и выполнение требований к чекам. Согласовать, кто формирует и передаёт чек НПД/«Мой налог», и проверить его на реальном тестовом сценарии. HTTP-ответ об оплате не является чеком; наличие ключей API не означает, что фискальные обязанности выполнены. Сервер блокирует рабочую конфигурацию без явного подтверждения подключённых чеков.
3. **Сервер оплаты.** Развернуть [backend](../backend/) на собственном HTTPS-домене. Секрет YooKassa и закрытый ключ подписи лицензии хранятся только на сервере, вне APK/Git. Проверить подлинный статус, сумму 99.00 RUB, получателя и тип `sbp` у провайдера. Возврат из браузера и статус от клиента сами по себе не выдают Pro.
4. **Реклама.** Создать собственный блок Яндекса, проверить условия рекламного договора, сведения для выплат и обязательные раскрытия данных. SDK получает IP и технические данные устройства; нельзя рекламировать `store` как приложение совсем без передачи данных. Текст, настроение, теги, векторы и поисковые запросы не включаются в рекламные запросы.
5. **Публичные документы.** Опубликовать согласованные политику конфиденциальности, условия платного доступа, порядок возвратов и контакты. Проверить URL без входа в аккаунт. Текст до оплаты должен явно сообщать 99 ₽/месяц, ручное продление, отсутствие автосписаний и состав Pro. Возрастные/географические требования провайдеров оценить по договору.

Официальные точки проверки: [RuStore для разработчиков](https://www.rustore.ru/developer), [требования к приложениям](https://www.rustore.ru/help/developers/publishing-and-verifying-apps/requirement-apps), [YooKassa для самозанятых](https://yookassa.ru/self-employed/), [приём платежей СБП](https://yookassa.ru/developers/payment-acceptance/scenario-extensions/sbp). Это ссылки для проверки условий владельцем, а не подтверждение уже заключённых договоров.

## Настройка и сборка

Публичные параметры задаются Gradle properties, значения по умолчанию пустые:

```sh
./gradlew assembleStoreDebug testStoreDebugUnitTest \
  -PYAN_AD_UNIT_ID=собственный_рекламный_блок \
  -PPAYMENT_BACKEND_URL=https://payments.example.org \
  -PPRO_LICENSE_PUBLIC_KEY=публичный_ключ_проверки_лицензии
```

`example.org` и поясняющие значения — шаблон команды, их нельзя использовать в выпуске. В APK помещается только публичный ключ проверки, не закрытый ключ и не `YOOKASSA_SECRET_KEY`. Флаги `productionConfigured` в конфигурации выпуска описывают подтверждённую настройку, сами ничего не включают в приложении.

Технический кандидат без ключа владельца:

```sh
bash scripts/build_release.sh store --unsigned-candidate
bash scripts/build_release.sh offline --unsigned-candidate
python3 scripts/check_release_readiness.py --report-only
```

Неподписанные кандидаты нельзя загружать как законченный пользовательский релиз. Для конечной сборки использовать [собственный ключ](SIGNING.md), сохранить его резервную копию вне Git и передать production-параметры. На итоговом `offline` проверить отсутствие INTERNET, на `store` — ожидаемые разрешения и состав SDK, на обоих — отсутствие отладки, встроенную модель, подпись, миграции и отсутствие debug-only экранов.

Проверка готовности принимает отчёты проверки **store** APK/AAB. Она сохраняет блокировку до заполнения данных владельца, настройки провайдеров и чеков, публичной политики, раскрытия сторонней оплаты, тестирования и подписи. JSON-описание настройки и отчёт не доказывают, что сервер действительно развёрнут: нужны реальные проверки.

## Проверки перед отправкой

- Выполнить [инструкцию модерации](REVIEWER.md) на физических устройствах: чистая установка, миграция, авиарежим, закрытие рекламы/уход в фон, отмена оплаты, успешный СБП, потеря сети, повторная проверка статуса, восстановление Pro и истечение срока. Проверить границы месяцев и срок доступа, показанный до/после платежа.
- Подтвердить, что при неуспешной рекламе/оплате бесплатные функции доступны. Pro должен активироваться по проверенной подписи сервера и работать офлайн до выданного срока; после окончания недоступна только статистика и возвращается возможность показа рекламы.
- Настроить тестовый доступ модерации средствами серверного тестового окружения и магазина. Не встраивать универсальный PIN, локальный переключатель Pro или тестовые секреты в production APK.
- Подготовить изображения реального интерфейса с вымышленными записями. Сохранить `FLAG_SECURE` в пользовательском приложении.
- Заполнить анкету рекламы, разрешений, данных и сторонних платежей по фактической сборке. Отправить на модерацию после сверки пакета и договоров; публикация не выполняется автоматически скриптами.

## Переход с GitHub-сборок разработки

APK 0.6.x подписаны ключом разработки. Если релизный сертификат другой, Android не установит сборку с тем же package name как обычное обновление. Сначала сохранить черновики как записи, вернуть нужное из корзины и создать доступный зашифрованный `.pdiary` с собственным паролем. Только после сохранения копии переустанавливать приложение. Удаление удалит локальные данные и Keystore.

В новой установке создать PIN и восстановить копию. Переносятся сохранённые записи, даты, настроение, теги и избранное; индекс строится локально заново. Черновики, корзина, PIN и ключ устройства в копию не входят. Доступ Pro восстанавливается отдельно по секретному коду доступа через сервер; дневник на сервер при этом не отправляется. Код восстановления Pro следует хранить самостоятельно и не публиковать.
